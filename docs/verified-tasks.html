Verified tasks

When a result has to be machine-certified, it runs as a mission. The checks are frozen before execution, every step is approved, and a chat message can never satisfy a check.

Updated 2 November 2026 5 min read

When a result has to be machine-certified, it runs as a mission. The checks are frozen before execution, every step is approved, and a chat message can never satisfy a check.

The four shipped missions#

MissionInputsWhat it doesStatus
desk_taskGoal textChange approved workspace files and prove every change with a checkAccepted end-to-end with the real model
screen_qaScreenshot, written specCheck a screenshot against criteria and cite visible evidencehuman_review_only
voice_intakeAudio, output schemaTurn a spoken note into schema-valid JSON grounded in the transcripthuman_review_only
doc_extractDocument image, fieldsRead requested fields and prove each value is groundedhuman_review_only

Only desk_task has a completed real-model acceptance record. The three semantic missions are refused by the engine with a stated reason and the UI shows the badge with Start disabled. That is not a bug to work around; it is the qualification gate described below.

How a run executes#

  1. Freeze. The mission manifest plus your input produce a frozen acceptance contract with a hash. Nothing after this point can weaken it.
  2. Plan. The planner drafts steps bounded by the mission's limits.max_steps.
  3. Approve. You approve the plan before any step runs.
  4. Execute and verify. Each step's tool calls run and its deterministic checks are evaluated against the real workspace. Evidence records the digest of the file it actually read.
  5. Retry with a budget. A failed step consumes a retry under the recovery budget. A retry uses a different strategy where one exists; it never relaxes a check.
  6. Report. The run ends passed only when every frozen step check and the final output contract pass. The report carries the acceptance hash, per-step attempts, check evidence, observed versus expected output digests, and the journal count.

A run that cannot make progress ends incomplete with a reason such as no_progress and exits non-zero. It never reports a pass, and it never leaves a model process behind.

Check kinds#

Deterministic checks are evaluated against real files and digests:

CheckMeaning
file_existsThe named artifact is present
dir_existsThe named directory is present
content_matchesThe file contains a required term
content_absentThe file does not contain a forbidden term
json_schemaThe artifact validates against a frozen schema
numeric_consistencyNumbers in the output agree with the frozen input
report_completeEvery required section of a report is present

Semantic checks consult a bounded local judge. Each result carries provenance: the evidence chain (d1 or vl->d1), the model identity, the exact prompt and raw response, the label, the confidence in basis points, the frozen threshold, and the output pointers that were judged.

CheckJudgeQuestion
vl_criterionVision, then d1Does the image satisfy this written criterion?
d1_nould1Is this claim supported, unsupported, or ambiguous?
d1_choiced1Which label from a closed set applies?
d1_groundedd1Is each output field grounded in the immutable input?

Semantic evidence cannot manufacture a pass#

This is the part of the harness most worth understanding, because it is where a plausible-looking system usually cheats.

  • A mission must declare a semantic policy. Packaged missions using semantic checks declare mode: human_review_only, a minimum confidence, and a reason; the engine refuses to start them.
  • automatic passing requires a frozen holdout qualification: at least three packaged runs and zero confident false completions. No such qualification has been performed, so automatic passing is disabled everywhere.
  • d1_grounded first requires each field value to occur literally in the frozen input bytes. A fabricated value fails before any model is consulted.
  • An unavailable judge, an invalid protocol answer, low confidence, or an ambiguous verdict is error, which is never treated as a pass. A deterministic failure in the same step always wins.

Automatic semantic passing is off

You may see confidence numbers and judge responses in the evidence inspector. They are there to inform a human review. They cannot pass a run in this release, in any mission, on any machine.

The journal#

Verified runs are recorded in a SQLite journal in the trusted data directory. lfm3 status reads it directly:

lfm3 status              # most recent run
lfm3 status <run-id>     # one run
lfm3 status --events     # include the durable event journal

A run killed mid-attempt is left interrupted. The next run reconciles one run, one step, and one attempt, does not resume it, and then proceeds normally. There is no silent resume and no ghost step.

lfm3 retry creates a linked run with the same frozen acceptance contract. The link is recorded, so you can follow a retry chain without trusting a log line.

Fixtures and adversarial cases#

The desk_task fixture set under tests/fixtures/desk_task/ covers a passing run, a recoverable first-write failure, a wrong-content run that must never pass, and adversarial fixtures for an unsatisfiable required term and an output path outside the workspace. Expected facts live in tests/golden/desk_task/.

The packaged real-model acceptance records eight cases:

CaseResult
successExit 0, passed, one attempt, 5.99 s
failureExit 1, incomplete / no_progress, four attempts, no false pass
escapeExit 1 before planning, no file outside the workspace
retryExit 0, passed on attempt 2 after a denied first write
crashOwned model killed after attempt.started; no false pass
unavailableClosed loopback endpoint; exit 1, no owned server
timeoutOne-second deadline; owned server terminated
missingEmpty models directory; exit 1, no download, no server

Every case ended with no leftover PIDs and no surviving owned server. Replanning with the real model was not exercised in that run and remains covered by automated tests only.

Writing a mission#

A mission is one JSON file in the missions directory. The shipped desk_task is the shortest complete example:

{
  "schema_version": 1,
  "name": "desk_task",
  "version": 1,
  "title": "Workspace task",
  "description": "Change approved workspace files and prove every change with a check.",
  "inputs": {
    "goal": { "kind": "string", "required": true }
  },
  "tools": ["list_files", "read_file", "write_file", "edit_file"],
  "checks": ["file_exists", "dir_exists", "content_matches", "content_absent"],
  "command_templates": [],
  "output": {
    "schema": null,
    "required_artifacts": [{ "path": "out/summary.md", "non_empty": true }]
  },
  "limits": { "max_steps": 8, "max_attempts": 3 }
}

Rules the loader enforces:

  • Tools listed in the mission are the only ones granted, and path confinement still applies.
  • required_artifacts are the output contract. A run cannot pass without them.
  • limits cap the plan and the retries.
  • command_templates is empty for general work; missions that author shell commands are a separate, deliberately narrow surface.
  • A mission that uses semantic checks must declare a semantic policy with a mode, a confidence floor, and a reason.

Separation from chat#

ChatVerified task
Approval unitOne diffOne plan, then step evidence
CompletionThe model stopsFrozen checks and output contract
ProofTranscript, for a person to readJournal with digests and provenance
RetryYou send another messageBudgeted retry under the same contract
Can it pass work it did not do?n/aNo: checks read the real workspace

The engine is shared. The rules are not. Anything that must be certified belongs here, not in a conversation.
