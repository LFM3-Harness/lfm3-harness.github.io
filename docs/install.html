Install

Three packages, one engine. The installers carry the pinned llama.cpp runtime and no model weights, so the download stays small and the models arrive when you ask for them.

Updated 2 November 2026 5 min read

LFM3 Workspace ships as three packages built from one tag: a Windows installer, Linux desktop packages, and a headless Linux CLI archive. All of them include the pinned llama.cpp CPU runtime. None of them include model weights.

Requirements#

MinimumNotes
OSWindows 10/11 x64, or Linux x86_64No macOS or ARM build
Memory8 GBPractical minimum for chat with the text model; more helps with vision, voice, and routing
Disk250 MB for the appPlus about 4.9 GB for all four model roles
GraphicsNoneCPU inference only (-ngl 0)
Linux desktopWebKitGTK 4.1, GTK 3Declared as package dependencies; the .deb installs them
NetworkOnly for the download you startAfter setup the app works offline

The Linux CLI needs none of the desktop libraries. It runs on Ubuntu 22.04 or newer with a CPU-supported glibc.

Verify what you downloaded#

The published SHA-256 is the last line of defence before you run a binary. Check it once; it takes a few seconds.

Windows (PowerShell)

Get-FileHash .\LFM3.Workspace_0.1.1_x64-setup.exe -Algorithm SHA256

Linux

sha256sum LFM3.Workspace_0.1.1_amd64.deb

Compare the output with the table above. Every model file is verified separately by the app when it downloads weights.

Install on Windows#

  1. Run LFM3.Workspace_0.1.1_x64-setup.exe. The installer is unsigned, so Windows SmartScreen may show Windows protected your PC. Choose More info → Run anyway only if your checksum matches.
  2. The installer is per user and needs no administrator rights. It installs to %LOCALAPPDATA%\LFM3 Workspace and adds a Start-menu entry named LFM3 Workspace.
  3. Launch the app. It opens on chat with the bundled runtime detected and every model role marked Missing.
  4. Open Models and download at least the text role. See Models for the catalog.

The install path contains a space. That is deliberate and exercised by the project's installed smoke test, because paths with spaces break naive child-process handling.

Install the Linux desktop#

Debian or Ubuntu

sudo apt install ./LFM3.Workspace_0.1.1_amd64.deb
lfm3-desktop

The package declares its WebKitGTK 4.1 and GTK 3 dependencies, installs a desktop entry, and places the bundled llama.cpp runtime under the app's resource directory (/usr/lib/LFM3 Workspace/tools/llama). The shell seeds LFM3_LLAMA_SERVER and LFM3_LLAMA_TTS from that resource directory before the engine reads its configuration, and never replaces a path you set yourself.

AppImage

chmod +x LFM3.Workspace_0.1.1_amd64.AppImage
./LFM3.Workspace_0.1.1_amd64.AppImage

The AppImage carries the runtime inside its mount point and resolves it the same way it resolves an installed one. If your distribution lacks FUSE, run the archive with --appimage-extract and start the extracted AppRun.

Each harness-owned llama.cpp process gets its own directory at the front of LD_LIBRARY_PATH, so the packaged libggml*, libllama*, and libmtmd* are used even when a system copy exists.

Install the Linux CLI#

The CLI archive is not an installer. Unpack it anywhere and keep its layout:

tar -xzf LFM3-Workspace_0.1.1_linux-x64_cli.tar.gz
cd LFM3-Workspace-linux-x64
LFM3-Workspace-linux-x64/
  lfm3-cli              the headless binary
  run.sh                wrapper that sets the local runtime and models paths
  missions/             the four mission manifests
  tools/llama/          llama-server, llama-tts, CPU libraries, RUNTIME.txt
  models/               create this folder and put GGUF files in it

There is no model downloader in the CLI archive. Copy the pinned GGUF files into models/ beside run.sh, or point LFM3_MODELS_DIR at an existing weights folder, then check the setup:

mkdir -p models
./run.sh doctor
./run.sh missions
./run.sh models --probe

run.sh defaults LFM3_LLAMA_SERVER to tools/llama/llama-server and LFM3_MODELS_DIR to models when you have not set them. Every command in the CLI reference works through it.

First launch#

On boot the engine performs read-only discovery: an explicit path first, then the usual local locations for llama-server, llama-tts, the GGUF directory, and the vision projector. Discovery never downloads, copies, or contacts the network. The health report lists every missing item plus the resolved workspace and models directory.

To override discovery, either set environment variables (documented in Configuration) or write setup.json into the data directory.

The data directory and the install directory are separate. Removing the app does not delete your transcripts, journals, or weights; the next section explains how to remove those deliberately.

Update#

Installing a newer build over an existing one keeps %LOCALAPPDATA%\LFM3Harness (or the XDG equivalent) intact: transcripts, journals, jobs, settings, and weights are all in the data directory, not beside the binary. On Linux, install the newer .deb with the same apt install command, or replace the AppImage file.

Nothing updates itself. The app never checks for updates and never downloads a release in the background.

Remove it#

Windows. Open Settings → Apps → Installed apps → LFM3 Workspace → Uninstall, or run uninstall.exe from the install folder. Then delete %LOCALAPPDATA%\LFM3Harness if you also want the transcripts and weights gone.

Linux desktop. Find the installed package name, then remove it:

dpkg -l | grep -i lfm
sudo apt remove <package-name>

Delete $XDG_DATA_HOME/LFM3Harness (usually ~/.local/share/LFM3Harness) to remove state and model weights.

Linux CLI. Delete the unpacked folder. Nothing outside it is created unless you set LFM3_DATA_DIR.

Keep the runtime out of backups

The model weights are large and replaceable. If you back up your home directory, exclude the models folder inside the data directory to avoid copying several gigabytes per snapshot.

What the installers contain#

Both desktop bundles ship missions/ plus the pinned CPU llama.cpp runtime: llama-server, llama-tts, the CPU backends, and the platform runtime libraries — the VC++ DLLs on Windows and the ELF shared libraries on Linux. The 594 MB CUDA backend, development tools, and all GGUF weights are excluded.

Nothing is code-signed. That is a funding decision, not a claim about safety: verify the SHA-256 and read the source, which is MIT-licensed and published in full.

Networking during install#

The installer itself makes no network calls. The only outbound traffic in the entire product is:

  1. Model downloads you start from Models, pinned to huggingface.co/LiquidAI with fixed names, lengths, and SHA-256 digests.
  2. A link you click in the interface.
  3. Opt-in PostHog tracing, when you set POSTHOG_API_KEY yourself.

The Tauri CLI fetches its own packaging tooling at build time, never from the installed application. Details and caveats are in Privacy, security, and licensing.
