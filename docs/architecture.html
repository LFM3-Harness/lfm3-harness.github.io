Architecture

One process tree, no sidecar, no loopback control server. The webview talks to an embedded engine through typed commands and listens to durable events.

Updated 2 November 2026 5 min read

One process tree, no sidecar, no loopback control server. The webview talks to an embedded engine through typed commands and listens to durable events.

The shape of it#

React + TypeScript UI
  chat · attachments · voice · verified tasks · jobs
        │ typed Tauri commands and events
        ▼
Tauri 2 desktop application
  chat runtime · routing · approval gates · durable events
        │ embeds in-process
        ▼
Rust lfm3-harness engine
  chat transcript store · decision router · search and related tools
  planning · execution · verification · retries · model leases
  SQLite run journal, chat.db, jobs.db · artifacts
        │ owns child processes
        ▼
llama.cpp b11960 / v0.8.0
  LFM3-1.7B · LFM3-VL-2B · LFM3-Audio-2B · d1-2B
  llama-server for chat, vision, hearing, and routing
  llama-tts for LFM3-Audio-2B speech output

Production uses no Python sidecar and no localhost engine HTTP server. The headless CLI uses the same Rust harness for diagnostics and real-model acceptance.

Components#

apps/ui — the interface#

React 19, TypeScript 5.9, and Vite 8. It opens on chat, shows the decision route and local model roles, accepts image attachments and voice input, reads answers aloud with the local voice, and keeps verified missions one click away. The production bundle contains no demo bridge; ?demo=1 exists only in development and renders the verified-task surface with chat unavailable.

apps/desktop — the shell#

The Tauri 2 shell embeds one engine and exposes typed commands and durable events to the webview. It runs the multi-model chat turn loop and the approval gates, and it owns every child process through a kill-on-close Windows Job Object or a Linux process group.

Key modules:

FileResponsibility
src-tauri/src/commands.rsThe typed command surface the webview may call
src-tauri/src/chat.rsChat turn loop, routing, gates, attachments, voice

crates/lfm3-harness — the engine#

The engine is a plain Rust library, which is why the desktop app and the CLI cannot drift apart:

  • frozen acceptance contracts and mission manifests;
  • planning, execution, verification, and the recovery controller;
  • confined tools and the shared path resolver;
  • provenance-bound deterministic checks and the semantic judge contract;
  • model leases and process supervision;
  • the SQLite run journal and the chat transcript store.

crates/lfm3-cli — the headless binary#

doctor, missions, models, plan, run, status, retry, task, and job. It links the same engine and uses the same configuration loader.

A chat turn, in order#

  1. The webview calls a typed command with the message and any attachments.
  2. The engine opens or resumes the conversation in chat.db and checks that no turn is already live.
  3. If d1 is installed and the message is long enough, the router classifies it against a closed label set. The keyword route stands if the answer is missing, slow, or below the floor.
  4. The acting model is called with a bounded context: fixed system prompt, newest 240 messages capped near 96,000 characters, temperature 0.3, at most 1,024 output tokens.
  5. Tool calls are executed by the confined registry. Reads run; writes become pending actions after the write gate.
  6. Tool results, gate outcomes, and message deltas are emitted as durable events.
  7. The turn ends after at most twelve tool rounds, or on Stop, which cancels the stream and pending approvals.

A verified run, in order#

  1. The mission manifest plus input produce a frozen acceptance contract and its hash.
  2. The planner drafts steps; the plan is approved before execution.
  3. The executor runs one step at a time, each tool call path-confined.
  4. The verifier evaluates deterministic checks against real files and records digests; semantic checks follow the mission's declared policy.
  5. Failures consume the recovery budget and may replan, never relax.
  6. The coordinator writes every transition to the journal and emits events.
  7. The run ends passed only on a complete contract, otherwise incomplete with a reason.

Event channels#

ChannelCarries
lfm3:chat-eventChat message deltas, route and gate results, approval requests and decisions, voice results
lfm3:job-eventJob turns, phases, todo state, tool calls, status
lfm3:run-eventVerified-run journal events: attempts, checks, retries, completion

Events are durable, not cosmetic: the journal and the database are the source of truth, and the UI rehydrates from them after a restart.

Process supervision#

Model servers are child processes the harness owns, not services you manage.

PlatformMechanismOn exit
WindowsJob Object with kill-on-closeThe entire job is terminated
LinuxProcess group per childThe group is terminated

A platform with neither containment refuses to start children rather than leaking them. The supervisor reports which mechanism it is using. On Linux, each owned llama.cpp process also gets its own directory at the front of LD_LIBRARY_PATH, so packaged libraries win over system copies.

The installed smoke acceptance proves this in the negative: an externally started llama-server survives every phase, while an owned llama-server dies with the app.

State#

StoreContents
chat.dbConversations, messages, pending and decided approvals
jobs.dbJobs and their turns
runs.dbRuns, steps, attempts, evidence, retry links
setup.jsonRuntime paths, models folder, default workspace
WorkspaceOnly approved writes, plus .attachments/

No store is shared with the model servers, and no model output is trusted as state. The engine reads the file it wrote to report a digest, rather than trusting the content it sent.

Why it is built this way#

  • Embedded, not sidecar. A separate engine process would add a supervisor, an RPC surface, and a second lifecycle to get wrong. An in-process engine makes the boundary a function call.
  • One path resolver. Tools and verifiers share paths::resolve, so "inside the workspace" cannot mean two different things.
  • Typed decisions. Routing and gates return declared labels with confidences, not free text. An undeclared label is a failure, not an interpretation.
  • Measured completion. Every completion claim is re-derived from the filesystem. The digest in a report is recomputed from the file that was re-read.
  • Bounded everything. Turns, tool calls, tool output, file sizes, retries, deadlines, and plan size all have caps. The model's profile sets them.

Stack#

  • Rust stable: MSVC toolchain on Windows, GNU on Linux.
  • Tokio, Serde, Reqwest, Rusqlite, and SHA-256 for the engine.
  • Tauri 2 for the native boundary.
  • React 19, TypeScript 5.9, Vite 8, Vitest, and Playwright for the UI.
  • External llama.cpp b11960 for inference: no Rust FFI, no version drift.

The inference backend is pinned deliberately. Using Rust does not require changing llama.cpp, and an upgrade requires a separate compatibility qualification across all four models.
