Build from source

Rust stable, Node.js 22, and Tauri 2. The desktop app, the CLI, and this documentation all build from the same checkout.

Updated 2 November 2026 4 min read

Rust stable, Node.js 22, and Tauri 2. The desktop app, the CLI, and this documentation all build from the same checkout.

Prerequisites#

ToolVersionNotes
RuststableMSVC toolchain on Windows, GNU on Linux
Node.js22Used by the UI and the Tauri CLI
Tauri CLI2.xInstalled as a dev dependency of apps/desktop
WindowsMSVC build toolsFor the Rust toolchain and the final bundle
LinuxWebKitGTK 4.1, GTK 3Required to build and run the desktop shell

The cargo workspace must be on PATH for the Tauri CLI.

Development loop#

npm --prefix apps/ui install
npm --prefix apps/desktop install
cd apps/desktop
npx tauri dev

Vite serves the UI on 127.0.0.1:1420; the Tauri window is 1280×1000 with a 960×720 minimum. The shell embeds the engine, so there is no second server to start.

On Windows, run.bat wraps the same commands:

.\run.bat              # Vite + embedded Rust backend
.\run.bat app          # the already-built application
.\run.bat cli doctor   # any CLI command
.\run.bat build        # NSIS installer

On Linux, ./run.sh desktop starts the same UI and installs a private Node.js LTS under .tools/linux-node when needed. ./run.sh deps prints the exact WebKitGTK package command for your distribution.

Tests#

cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

cd apps/ui
npm run typecheck
npm test             # Vitest
npm run build
npx playwright test

What each gate covers:

GateCovers
Workspace testsEngine, tool confinement, verification, recovery, desktop commands, job lifecycle
VitestReducers, message rendering, routing, job checks, model menu, workspace switching
PlaywrightThe verified-task demo scenarios in the browser
Clippy with -D warningsLint cleanliness, not style preference

Model-dependent tests are marked ignored and run when the pinned weights are present. A test that needs a model does not silently skip and report success.

Packaging#

Windows NSIS installer

cd apps/desktop
npx tauri build --bundles nsis

Output: target/release/bundle/nsis/LFM3 Workspace_0.1.1_x64-setup.exe.

Linux .deb and .AppImage

./run.sh bundle

Output: target/release/bundle/deb/*.deb and target/release/bundle/appimage/*.AppImage. tauri.linux.conf.json selects those targets.

Both bundles stage missions/ and the pinned CPU runtime through scripts/stage-llama-runtime.mjs. The staging step makes no network calls; RUNTIME.txt lists every staged file and the pinned build.

CI. .github/workflows/release.yml builds all four assets from one tag and publishes them together, appending a checksum table generated from the uploaded files to the release body.

Release acceptance#

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/accept.ps1

In order, it runs: cargo fmt --check, clippy with warnings denied, the full Rust workspace tests, a check that no Python project files remain, UI typecheck and unit tests, Playwright end-to-end tests, the Tauri NSIS build, and the installed smoke acceptance.

Use -SkipUi, -SkipE2e, -SkipBuild, or -SkipSmoke for partial runs. A full run on the release machine took 170.0 s; a static and UI-only rerun took 29.2 s.

The installed smoke acceptance (scripts/smoke.ps1) installs the NSIS build silently into a path containing spaces and drives the packaged executable's probes: a real desk_task start and cancel, a refused overlapping start, an interrupted run reported correctly on the next boot, and process containment when the app is force-terminated. It also asserts that an externally started llama-server survives every phase.

Known gaps

Semantic holdout qualification has not been performed, so automatic semantic passing is disabled and three missions are human_review_only. Real-model replanning is covered only by automated tests. In-app playback of the LFM3 voice is covered by component and runtime tests, not by the headless probe or the Tauri webview.

This documentation#

The pages under /docs are generated from docs/guide/*.md. Navigation order, page titles, descriptions, and the ledes live in scripts/build-docs.mjs; the markdown holds only content.

node scripts/build-docs.mjs          # rewrite the HTML, search index, and sitemap entries
node scripts/build-docs.mjs --check  # fail if the committed output is stale

The generator supports a deliberately small markdown subset: ## and ### headings, paragraphs, bold, italic, inline code, links, fenced code, unordered and ordered lists, tables, ---, and callouts:

::: note Optional title
Body text, with normal inline formatting.
:::

Variants are note, tip, warn, and danger. Heading ids are generated from the heading text, so cross-page links can point at page.html#section and stay stable. Links ending in .md are rewritten to .html automatically.

The build also writes docs/search-index.json for the in-page search and updates the generated block in sitemap.xml. Nothing is fetched at runtime, and the output is plain HTML with one small script for search, copy buttons, and scrollspy.

Adding a mission#

  1. Copy a manifest in missions/ and change name, inputs, tools, checks, and output.
  2. Validate it with lfm3 missions.
  3. Add fixtures under tests/fixtures/<mission>/ and expected facts under tests/golden/<mission>/.
  4. Run the fixture suite, then a real-model acceptance before claiming the mission is supported.
